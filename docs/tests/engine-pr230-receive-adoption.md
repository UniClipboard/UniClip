# Engine PR #230 adoption: per-item receive results and selected retry

Mobile pins Engine `5cbca8fc24a278fa7b01ae611bf4b925914bef13`, the merge commit of
Engine PR #230 (`feat(blob): manage transfers and retry partial receives`). The module
label stays `v1.1.0-rc.23`; the full source commit is authoritative. The previous Mobile
pin was `a8e1b2c912cebbbb835049d3bc343cfe9a036bb7`.

This note records what changed, which semantics the host preserves, the platform
coverage of the prepared native artifacts, what was verified, and what was not run.
The failure model and the planned entry points were written first in
[engine-receive-results-acceptance.md](engine-receive-results-acceptance.md).

## What changed

| Layer | Change |
| --- | --- |
| Pin | `modules/uc-engine/core-source.json` points at the merge commit. No local override, no absolute path. |
| Generated bindings | `uc_engine_uniffi.swift` and `uc_engine_uniffi.kt` are regenerated by `npm run core:prepare` together with the native libraries. They are ignored build outputs. |
| Native bridges | `UcEngineModule.swift` and `UcEngineModule.kt` expose `queryEntryReceiveProgress`, `listEntryReceiveProgress`, `retryEntryReceive` and `cancelEntryReceive`. Retry returns Engine failures as data like the other space operations. |
| JavaScript API | `modules/uc-engine/src/index.ts` adds the receive types and four functions. Fixed Engine strings pass through unchanged. |
| Host service | `ReceiveResultsService` (`src/features/transfer/internal/receiveResults.ts`) mirrors Engine snapshots into `useReceiveResultsStore`. Events only invalidate; every state is read back from the Engine. |
| UI | `ReceiveResultsSheet` (Android and iOS files) shows each item and its own result, with cancel and retry-selected. `HomeOverlays` owns it. The existing Home top-bar menu gains a "Received files" entry only while receive attempts exist. |
| Binding E2E | `e2e/engine-settings` gains a seventh `receive-api` case. |

## Semantics the host keeps

- `accepted` means the Engine took a new attempt. The sheet says a retry started and shows
  an item as saved only when the Engine reports `completed` for it.
- A `failed` or `cancelled` attempt can still contain delivered files. Delivered items stay
  completed and are never selectable. Unselected failures stay failures.
- A directory is one `directory_unit` item. The sheet offers it as one unit; member counts are
  shown separately and never as item counts.
- `cancellation_incomplete` is never shown as cancelled. The attempt stays non-terminal and
  offers neither retry nor a second cancel until a later snapshot says otherwise.
- Item identities and the expected attempt come from the current snapshot. The host never builds
  an item id from a file name or path. A stale attempt is answered by the Engine with `superseded`.
- After a restart the Engine may return `unavailable` / `source_unavailable`. The host keeps the
  failed items and saved files and says the source is no longer available.
- Events only invalidate. A late event for an old attempt triggers a query and is never copied
  into state. An older query response that completes after a newer one is dropped.
- State is rebuilt with the list query on start, on `refreshRequired`, and whenever the engine
  reports `running` again (foreground resume). A failed query keeps the last snapshot and marks
  it stale.
- Sender `resendEntry` and receiver `retryEntryReceive` remain separate operations.
- The 120-second outbound UI wait does not cancel Engine work, and sender ACK is not used as a
  per-file receiver save receipt. No JavaScript downloader or second retry scheduler was added.
  Android foreground-service ownership and the iOS App Group ownership are unchanged.

## Not available in the Engine snapshot

The receive snapshot has no file names, sizes per item or timestamps. Rows are therefore
labelled "File 1", "File 2" and the entries "Transfer 1", "Transfer 2". Names exist only in the
transient `incomingPending` event. Showing names needs an Engine contract change.

`cancelInboundTransfer` (per transfer id) is not bridged: the snapshot carries item ids, not
transfer ids, so there is no honest mapping from a row to that call.

## Platform coverage of prepared artifacts

See the verification receipt for hashes. The coverage rule is: generated bindings and every
native slice come from one `core:prepare` run of one commit, and `core:verify` rechecks the
hashes.

| Platform | Slices |
| --- | --- |
| iOS XCFramework | `ios-arm64` (device), `ios-arm64_x86_64-simulator` (fat simulator) |
| Android AAR | `arm64-v8a` and `x86_64`, matching the module's declared `abiFilters`, built with `UC_ENGINE_UNIFFI_ANDROID_ABIS="arm64-v8a x86_64"` |

The default `core:prepare` builds `arm64-v8a` only. An AAR without `x86_64` does not support an
x86_64 emulator even though Gradle lists that ABI; do not claim x86_64 runtime from it.

## Reproduce

```sh
UC_ENGINE_REPOSITORY=/absolute/Engine npm run core:prepare
UC_ENGINE_UNIFFI_ANDROID_ABIS="arm64-v8a x86_64" npm run core:prepare -- --platform android
npm run core:verify
node scripts/validate-unified-engine-core-source.mjs
python3 e2e/engine-settings/run.py --engine-source /absolute/engine-at-pin \
  --target-dir /absolute/task-owned-target
npm run type-check && npm run lint && npx jest
```

The second command needs the Android entry removed from the prepared marker first, otherwise
the existing reuse check skips the build.
