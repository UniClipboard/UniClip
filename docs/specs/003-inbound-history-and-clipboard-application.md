# Spec - 入站历史与系统剪贴板写入

状态: 待二次确认

日期: 2026-08-16

实现基线: Expo SDK 56、React Native 0.85、Engine `v1.1.0-rc.3`
(`b390487672caa97a57a28657b22d3900bf5631f1`)

关联文档:

- `docs/specs/001-show-my-space-before-refresh.md`
- `docs/specs/002-device-trust-reconciliation.md`
- `docs/specs/unified-share-flow.md`
- `docs/tests/mobile-engine-upgrade-compatibility.md`
- Engine `docs/architecture/architecture-bible.md`

本规格重新定义移动端首页历史、远端接收和系统剪贴板写入之间的关系。实现完成后，
本规格替代 `CONTEXT.md` 中“移动端 SQLite 历史独立拥有历史事实”的现状描述，也替代
`unified-share-flow.md` 中由移动端历史落库决定内容是否进入首页的部分；分享页、待发送
队列和设备选择规则保持不变。

---

## 1. 目标

1. 任何内容只要已经被本机 Engine 可靠保存，就能出现在首页历史中。
2. “接收并保存”与“自动写入系统剪贴板”成为两个独立结果。
3. 用户关闭“自动写入本机剪贴板”后，远端内容仍正常接收、保存和展示。
4. 系统剪贴板写入失败不丢历史，不让发送端误报失败，也不依赖剪贴板监听补录历史。
5. 首页在漏掉事件、应用重启、回到前台和下拉刷新后，都能恢复完整历史。
6. Engine、主应用和 iOS 扩展只保留一个最终历史事实来源，同时兼容现有 App Group
   数据和本地 payload。
7. 图片、文件等多表示内容按用户操作意图展示，避免截图因为同时带文件表示而显示成
   普通文件。

## 2. 非目标

- 不把一台设备的完整历史自动复制到其他设备；历史事实仍是本机范围。
- 不改变空间成员资格、加密、传输门禁或设备信任规则。
- 不把“自动写入”开关改成“是否接收”开关。
- 不要求系统剪贴板支持所有 Engine 已能保存的格式。
- 不增加独立“置顶”功能，不保留按使用次数排序。
- 不在本规格中重做首页卡片视觉、搜索界面或分享页布局。
- 不通过清空历史、删除 App Group、卸载重装或重新加入空间完成迁移。

## 3. 已确认现状与缺口

### 3.1 当前入站顺序

当前 Engine 对新内容已经按以下顺序工作:

```text
收到远端内容
  -> 校验和准备资源
  -> 保存 Engine 历史
  -> 安排异步系统剪贴板写入
  -> 不等待写入结果，发出 incomingEntry
```

系统写入任务和事件都发生在保存之后，但两者的实际完成先后不确定，也不应互相等待。
问题在移动端：首页只读取自己的
`clipboard_history`，而这份数据库通常由系统剪贴板监听成功后才新增记录。
`incomingEntry` 只触发首页重读同一份旧数据库，没有读取 Engine 已保存的条目。

因此会出现以下已复现结果:

```text
Engine 历史: 有图片
发送端: 显示接收方已接收
Android 系统剪贴板写入: 失败
移动端 SQLite: 没有新增
首页及下拉刷新: 看不到图片
```

### 3.2 当前设置没有真正控制入站写入

设置文案已经承诺“关闭自动写入后，内容只在首页出现”。但 `autoApplyRemote` 当前主要
参与后台任务是否运行的合并判断，没有作为普通前台接收的写入策略交给 Engine。
Android 只收到合并后的后台开关，iOS 对应方法还是空操作。因此前台、后台和文案不是
同一套规则。

### 3.3 当前有两份历史事实

- Engine 已经拥有条目编号、内容表示、资源、活动时间、收藏、删除、搜索、投递和保留策略。
- 首页、相机、图库、Process Text、分享入口、键盘扩展又直接读写移动端/App Group 历史。
- iOS 扩展在 Engine 暂不可用时还需要 App Group 数据离线展示和暂存。

不能继续让两份数据各自决定“历史里有什么”，也不能直接删除移动端历史破坏升级、冷启动
和扩展。

### 3.4 图片与文件分类混在一起

Engine 当前从全部内容表示中计算一个物理类别，优先级是
`file > image > rich text > text > other`。当截图同时含文件地址、PNG 和 TIFF 时，条目会被
归为文件，即使预览实际选择了图片。这说明“内容能以什么形式传输”和“首页应怎么展示”
必须分开。

## 4. 核心不变量

以下规则不得由平台、前后台状态或内容类型改变:

1. **可靠保存是历史可见的唯一门槛。** 系统剪贴板变化不是门槛。
2. **自动写入是保存之后的可选本机动作。** 关闭或失败都不能撤销保存。
3. **发送成功只证明接收方可靠保存。** 不证明接收方首页当时已经渲染，也不证明其系统
   剪贴板已改变。
4. **事件只表示历史已经失效。** 首页收到事件后重新查询完整的最终状态，不用事件载荷
   自行拼历史。
5. **漏事件不能丢内容。** 启动、回前台和下拉刷新必须能从持久状态恢复。
6. **同一内容只有一个最终条目身份。** 传输重试不新增、不重排；用户稍后再次激活同一内容
   时复用身份并移到顶部。
7. **未完整保存的内容不能报告接收成功。** 接收中的占位卡片不是历史事实。
8. **投影可以删除重建，最终历史不能靠投影反推。** 唯一例外是尚未被 Engine 接纳的扩展
   暂存记录。
9. **首页历史与空间连接解耦。** 离线、无空间或设备刷新失败时，本机历史仍可用。
10. **迁移不得静默丢数据。** 原历史、删除标记和 payload 在正式验收前都必须可恢复。

## 5. 所有权

### 5.1 Engine 负责

- 本机最终历史中的条目身份、内容哈希、来源和活动时间；
- 内容表示、资源可用性、缩略图、图片尺寸、文件集合和展示类型；
- 新增、重复、再次激活、软删除、收藏、搜索、清空和保留数量；
- 接收是否已可靠保存，以及发送端可见的接收结果；
- 是否尝试写系统剪贴板、写入结果和活动剪贴板状态；
- 本地入口和扩展暂存内容的幂等导入；
- 历史版本号以及“历史已变化”事件。

Engine 历史是**本机权威**，不是全空间共享数据库。设备离线、退出空间或切换空间后，本机
已有历史继续可用；是否向其他设备发送新内容仍由当前空间规则决定。

### 5.2 移动端主应用负责

- 冷启动先展示最后一次确认的本机投影，再与 Engine 对账；
- 查询分页历史、详情和资源，生成首页展示模型；
- 消费历史失效事件，在启动、回前台和下拉刷新时重新查询；
- 保存仅用于展示的可重建投影，不在投影中重新判断新增、重复、删除或保留；
- 把设置中的自动写入、后台接收和历史数量分别传给其真正负责人；
- 显示接收中占位、刷新失败和本机写入失败的短暂反馈。

### 5.3 App Group/移动端 SQLite 负责

目标状态下，它只承担:

1. 冷启动和扩展离线预览的可重建投影；
2. Engine 暂时不可用时，扩展新内容的有界暂存日志；
3. 升级迁移期间的旧数据档案和迁移记录。

它不得独立决定最终条目身份、删除、收藏、排序或清理。主应用从 Engine 对账后，Engine 结果
覆盖投影；投影中多出的非暂存条目不能反向写回 Engine。

## 6. 最终历史模型

### 6.1 条目最小字段

最终历史条目至少提供:

```ts
type HistoryEntry = {
  entryId: string;
  preview: string;
  physicalKind: 'text' | 'image' | 'file' | 'richText' | 'other';
  displayKind: 'text' | 'image' | 'file' | 'richText' | 'other';
  origin: 'localClipboard' | 'remote' | 'camera' | 'gallery' | 'share' | 'processText' | 'keyboard';
  createdAtMs: number;
  activeAtMs: number;
  sizeBytes: number;
  isFavorited: boolean;
  availability: 'complete' | 'partial' | 'lost';
  resource: HistoryResourceSummary | null;
};
```

- `physicalKind` 描述实际携带的主要传输能力，用于粘贴、保存和文件处理。
- `displayKind` 只决定首页展示。它不能由移动端根据文件名临时猜测。
- `createdAtMs` 表示第一次进入本机历史的时间。
- `activeAtMs` 表示最近一次真实用户激活或接收该内容的时间，首页默认按其倒序。
- 投递状态不是历史可见门槛；历史卡片不展示永久的系统剪贴板写入错误。

### 6.2 展示类型规则

内容入口应携带稳定的 `presentationIntent`:

| 入口                         | 意图    |
| ---------------------------- | ------- |
| 相机、图库、明确的图片分享   | `image` |
| 文件选择器、明确的文件发送   | `file`  |
| Process Text、明确的文本分享 | `text`  |
| 系统剪贴板自动捕获           | `auto`  |

`auto` 的回退顺序固定:

1. 多文件、目录或只有文件表示时显示为文件；
2. 单个可预览图片文件且同时存在有效图片表示时显示为图片；
3. 否则使用 Engine 已选定的预览表示类型；
4. 无法识别时显示为其他内容。

意图随条目保存并随远端内容传递。接收端不得因自身平台表示顺序不同而改成另一种展示类型。
旧发送端没有携带意图时按 `auto` 处理；新字段必须可选且版本化，不能让旧版本内容无法接收。

### 6.3 收藏、置顶和使用次数

- 收藏继续由 Engine 保存，并免于按数量或时间自动清理。
- 旧数据中 `pinned=true` 的条目迁移为收藏，确保用户保护的内容不被清理。
- 目标模型不提供第二个“置顶”状态。
- `useCount` 不迁入最终历史，不参与排序或保留；旧值只留在迁移档案中供回滚核对。

### 6.4 删除

用户删除条目时，Engine 先保存软删除标记，默认查询立即隐藏该条目。删除还要同步清理搜索
结果和受管资源，但清理失败不能让已删除条目重新出现在首页。

- 被动投影恢复、旧数据库导入和重复事件不得清除软删除。
- 用户后来再次复制、分享或从远端再次激活同一内容，属于新的用户动作，可以清除软删除、
  更新 `activeAtMs` 并复用原条目身份。
- 传输重试和应用重启不属于新的用户动作，不能复活条目。
- 软删除保留期必须覆盖支持的回滚窗口；物理清理只能由统一保留策略执行。
- “清空历史”是同一规则的批量操作，不能绕过软删除后让旧投影重新导入全部内容。

## 7. 入站接收与系统剪贴板写入

### 7.1 统一接收流程

```text
远端内容到达
  -> 接收门禁和内容校验
  -> 可选显示“正在接收”
  -> 完整资源落盘并提交最终历史
  -> 返回“已可靠保存”给发送端
  -> 发出 historyInvalidated
  -> 按本机设置决定是否尝试写系统剪贴板
  -> 单独记录本机写入结果
```

历史提交、发送端确认和历史失效事件不能等待系统剪贴板写入。系统剪贴板写入可以异步完成。

### 7.2 自动写入规则

| `autoApplyRemote` | 保存结果 | 系统剪贴板结果 | 首页           | 发送端   |
| ----------------- | -------- | -------------- | -------------- | -------- |
| 关闭              | 成功     | 不尝试         | 显示条目       | 接收成功 |
| 开启              | 成功     | 成功           | 显示条目       | 接收成功 |
| 开启              | 成功     | 失败           | 显示条目       | 接收成功 |
| 任意              | 失败     | 不尝试         | 不新增最终条目 | 接收失败 |

补充规则:

- `autoApplyRemote` 只控制远端内容是否自动写入系统剪贴板，不控制是否接收、保存或运行 Engine。
- 前台和后台使用同一个值。后台能力只决定当时能否接收或执行写入，不改变产品含义。
- 关闭自动写入是正常选择，不提示错误。
- 开启时写入失败，前台可显示一次短暂提示“内容已收到，但未写入剪贴板”；后台只记录诊断，
  不生成永久历史错误。
- 用户在历史卡片上主动点“复制”始终尝试写入，不受自动写入开关限制，并直接反馈结果。

### 7.3 活动剪贴板状态

本机活动剪贴板状态只在系统剪贴板实际写入成功后推进。关闭自动写入或写入失败时:

- 历史 `activeAtMs` 仍按本次真实接收或激活更新；
- 本机系统剪贴板保持不变；
- 本机不得向其他设备广播一个实际上没有写入的活动剪贴板状态。

### 7.4 接收、后台与方向开关

必须分开三件事:

| 设置/能力    | 负责内容                         |
| ------------ | -------------------------------- |
| 接收允许     | 本机是否接受远端内容             |
| 后台接收能力 | 应用不在前台时是否有机会完成接收 |
| 自动写入     | 保存后是否替换系统剪贴板         |

不得再把 `autoApplyRemote=false` 映射为拒绝接收或停止所有后台接收。平台在后台无法完成接收时，
回到前台后通过 Engine 对账恢复；不能用系统剪贴板内容补推历史。

## 8. 事件、刷新与首页状态

### 8.1 历史查询

Engine 对移动端提供带持久化单调 `revision` 的分页历史快照。revision 在同一用户数据目录内跨重启
继续递增。首页查询结果包含当前 revision；所有新增、
再次激活、删除、收藏、资源可用性变化和保留清理都会推进 revision。

同一轮刷新规则:

1. 保留当前可用列表，开始读取新 revision；
2. 分页结果必须来自同一 revision；中途变化则重启本轮读取；
3. 完整成功后原子替换内存状态并更新投影；
4. 失败时保留上次成功列表并显示可重试状态，不清空首页。

### 8.2 事件

目标事件语义为:

```ts
type HistoryInvalidated = {
  revision: number;
  reason: 'created' | 'resurfaced' | 'updated' | 'deleted' | 'retention';
  entryId?: string;
};
```

`entryId` 只用于移除接收占位和诊断，不能直接插入首页。多个事件可以合并成一次查询；事件丢失
也不影响最终恢复。

### 8.3 刷新触发

- 冷启动: 立即显示已确认投影，Engine 可用后对账。
- `historyInvalidated`: 前台合并刷新；后台记录待刷新。
- 回到前台: 无条件比较 revision，变化后刷新。
- 下拉刷新: 立即查询历史，不等待设备连接刷新。
- 设置数量、收藏、删除或本地导入完成: 由 Engine 事件触发同一刷新路径。

首页可以并行请求连接状态，但连接请求失败或超时不能阻塞历史刷新，也不能把历史列表清空。

### 8.4 接收中与部分内容

- `incomingPending` 只创建内存中的临时占位，不写最终历史投影。
- 完整保存后，`historyInvalidated` 让正式条目替换占位。
- 失败且 Engine 没有提交条目时，移除占位并显示一次接收失败。
- Engine 若保留可恢复的部分条目，首页可显示正式条目及“内容未完整”状态；它不写系统剪贴板，
  发送端也不能收到完整接收成功。
- 应用重启后不从临时占位恢复“正在接收”；只显示 Engine 已持久化的接收状态。

## 9. 重复内容与排序

| 场景                       | 条目身份   | 是否移到顶部 | 是否尝试自动写入 |
| -------------------------- | ---------- | ------------ | ---------------- |
| 新内容                     | 新建       | 是           | 按设置           |
| 同一次传输的快速重试       | 复用       | 否           | 否               |
| 同一内容经两条通道同时到达 | 复用       | 否           | 只允许一次       |
| 用户稍后再次复制同一内容   | 复用       | 是           | 按设置           |
| 已删除内容被用户再次激活   | 复用并复活 | 是           | 按设置           |
| 旧投影重复导入             | 复用       | 否           | 否               |

首页默认始终按 `activeAtMs` 倒序。重新收到旧内容时，内容第一次创建时间不变，只更新活动时间。
排序由 Engine 决定，移动端不使用自己的 `lastAccessed`、`useCount` 或 `pinned` 重排。

## 10. 本地内容入口

所有能让内容进入首页的本地入口最终都必须调用同一个 Engine 本地导入能力:

```text
importLocalContent(content, source, presentationIntent, idempotencyKey)
  -> 只保存/再次激活本机历史
  -> 不写系统剪贴板
  -> 不自动发送
  -> 返回最终 entryId 和 disposition
```

适用入口包括相机、图库、Process Text、系统分享、键盘扩展以及“分享取消后仍保留到首页”。
发送是导入之后的独立命令。导入成功不能宣称发送成功，发送失败或取消也不能撤销已经明确保留的
本地历史。

系统剪贴板监听仍可捕获真正的本机剪贴板变化，但必须直接提交 Engine。对 Engine 自己标记为
`RemotePush` 或用户从历史主动恢复产生的回声，不得再新增第二条移动端历史。

## 11. iOS 扩展与暂存交接

### 11.1 Engine 可用

扩展取得 Engine 运行权时，直接调用本地导入。Engine 返回最终 `entryId` 后，扩展更新 App Group
投影并继续原有分享/键盘流程。

### 11.2 Engine 不可用

扩展把 payload 和一条暂存日志原子写入现有 App Group 布局。暂存记录至少包含:

```ts
type StagedHistoryImport = {
  stageId: string;
  source: 'share' | 'keyboard';
  presentationIntent: 'text' | 'image' | 'file' | 'auto';
  payloadUri: string;
  contentHash: string;
  createdAtMs: number;
  state: 'pending' | 'importing' | 'failed';
};
```

- `stageId` 是导入幂等键。暂存成功只表示内容可恢复，不表示已进入最终历史或已发送。
- 扩展可以在离线投影中显示暂存内容，但要保留暂存身份；不能伪造 Engine `entryId`。
- 主应用启动或取得 Engine 运行权后认领暂存项，调用本地导入。
- Engine 确认成功后，投影用正式条目替换暂存项，再删除暂存日志；payload 只有在 Engine 已接管
  或明确不再需要时才清理。
- 导入失败保留暂存和 payload，按有界退避重试；用户删除暂存项时同时记录删除决定，避免下次
  启动重新导入。
- `pending -> importing -> confirmed` 的交接可重启、可重试且幂等；崩溃不能产生重复条目。

现有 App Group 目录、文件命名和原生应用兼容约定保持不变。新增元数据必须版本化，旧版本遇到
未知字段可以忽略。

## 12. 升级与迁移

迁移只能前进，必须有明确状态和恢复点:

```text
notStarted
  -> archived
  -> importing
  -> reconciled
  -> projectionActive
```

### 12.1 迁移步骤

1. 在原数据库同一事务中建立只读旧历史档案和迁移清单；不移动或删除 payload。
2. 为每条旧记录生成稳定幂等键 `legacy-mobile:<profileHash>`。
3. 普通记录通过本地导入进入 Engine；同内容已存在时复用 Engine 条目身份。
4. 合并用户状态: `starred || pinned` 迁移为收藏；活动时间取可信记录中的最新值。
5. 旧软删除记录迁入隐藏状态，防止投影对账把它们复活。
6. 保存 `profileHash -> entryId` 映射和每条结果；单条失败不标记整批完成。
7. 全量核对条目数、内容哈希、收藏、删除和 payload 可用性后，才启用 Engine 权威投影。
8. 重建投影后再次冷启动核对；第二次执行不得新增、复活或重排任何条目。

### 12.2 设置迁移

- 当前 `maxHistoryItems` 转为 Engine 唯一的按数量保留规则，最小值仍为 10。
- 收藏条目不计入自动淘汰候选。
- 因收藏条目受保护，首页总数可以超过 `maxHistoryItems`；设置文案必须明确它限制的是普通历史。
- 投影层停止执行 `cleanupByCount`、按年龄清理或孤儿历史决策，只清理确认不再被 Engine/暂存
  引用的缓存文件。
- 如果 Engine 设置迁移失败，保留原值和全部历史，不启用新的清理任务。

### 12.3 切换条件与回滚

- 迁移期间可以同时读取旧档案和 Engine 做对账，但同一时刻只有一方能决定首页最终列表。
- 在 `projectionActive` 之前继续使用旧首页；之后只使用 Engine 投影，不做长期双写。
- 旧档案至少保留到正式升级兼容验收完成后的一个发布周期；清理档案属于后续独立决策。
- 回滚只能切回完整旧档案，不得把已被新版本改写过的投影当成旧历史。

## 13. 失败处理

| 失败点             | 最终历史         | 系统剪贴板 | 用户可见结果                 |
| ------------------ | ---------------- | ---------- | ---------------------------- |
| 内容校验失败       | 不新增           | 不变       | 接收失败                     |
| payload 未完整落盘 | 不报告完整成功   | 不变       | 失败或可恢复的部分条目       |
| 历史提交失败       | 不新增           | 不尝试     | 接收失败                     |
| 历史事件丢失       | 已保存           | 按策略     | 下次对账恢复                 |
| 系统剪贴板写入失败 | 已保存           | 不变       | 前台短暂提示，不加永久错误   |
| 首页查询失败       | 已保存           | 不受影响   | 保留旧列表并可重试           |
| 投影写入失败       | 已保存           | 不受影响   | 当前内存可继续显示，下次重建 |
| 扩展暂存失败       | 未接纳           | 不变       | 明确失败，不宣称已保留       |
| 暂存导入中崩溃     | 未确认前保留暂存 | 不变       | 重启后幂等重试               |
| 保留策略失败       | 不删除           | 不受影响   | 记录诊断，下次重试           |

所有错误对外使用结构化类别。日志不得包含剪贴板正文、图片内容、文件路径、设备名或可还原内容的
哈希；现场诊断使用条目编号、流程编号、阶段、内容类别和大小区间。

## 14. 所需接口变化

Engine 和移动端绑定至少需要补齐以下完整能力，命名可按仓库约定调整，但语义不可拆散:

1. 带 revision 的历史分页查询、详情、资源、删除、收藏、统计和清空。
2. 本地只导入、不写剪贴板、不发送的幂等操作。
3. 入站保存策略中独立的 `applyToSystemClipboard` 决策，前后台共用。
4. 新增/再次激活/更新/删除/清理统一推进 history revision 并发出失效事件。
5. 最终条目同时提供 `physicalKind` 与稳定 `displayKind`。
6. 软删除和显式用户再次激活语义。
7. 投影重建所需的稳定条目身份、资源状态和活动时间。

不接受以下实现方式:

- 让移动端收到 `incomingEntry` 后再把事件内容手工插入旧历史；
- 在系统剪贴板写入失败时补写一条移动端记录作为旁路；
- 继续双写 Engine 与移动端历史并让“最后写入者”决定结果；
- 用 `autoApplyRemote` 关闭接收；
- 通过延时、再次下拉或轮询系统剪贴板掩盖事件错误；
- 删除旧数据库后重新开始。

## 15. 实施顺序

### 阶段 A: Engine 合同

- 完成历史 revision、展示类型、软删除、本地导入和独立自动写入策略。
- 保证新内容和再次激活都在可靠保存后发出同一历史失效事件。
- 用接收方持久化测试证明发送成功不依赖系统剪贴板。

### 阶段 B: 移动端能力与投影

- 同步 Engine 版本、Android/iOS/TypeScript 绑定和历史查询能力。
- 建立可重建投影、暂存日志和迁移清单。
- 首页仍未切换前完成真实旧数据迁移演练和重复执行验证。

### 阶段 C: 扩展交接

- 分享和键盘扩展改用直接导入或暂存交接。
- 验证主应用持有/不持有 Engine 运行权、扩展崩溃和主应用冷启动四种路径。

### 阶段 D: 首页切换

- 一次性把首页、搜索、收藏、删除、资源读取和下拉刷新切到 Engine 投影。
- 停止移动端历史清理和远端剪贴板监听补录。
- 更新 `CONTEXT.md` 和被本规格替代的分享历史描述。

### 阶段 E: 正式兼容验收

- 使用正式应用身份原地升级，不清数据。
- 完成 Android 与 iOS 真实设备、iOS 主应用与两类扩展、前后台和多设备接收验收。
- 对比升级前后历史数量、内容哈希、收藏、删除、payload 和设置，并完成两次冷启动幂等核对。

## 17. 完成标准

只有同时满足以下条件，才能宣称本规格实现完成:

1. Engine 单元和合同测试覆盖保存、事件、自动写入三者的独立结果。
2. Android 与 iOS 绑定从同一 Engine 提交生成并通过版本校验。
3. 首页不再通过系统剪贴板监听决定远端内容是否进入历史。
4. H-01 至 H-22 有记录在案的结果；涉及真实系统剪贴板、后台和扩展的项目必须在真实设备验证。
5. 发送端成功之外，至少有接收端 Engine 持久化和首页查询证据。
6. 升级测试保留原数据，第二次执行结果不再变化。
7. `CONTEXT.md`、设置文案和分享规格与最终所有权一致。

## 18. 二次确认项

进入实现前，需要确认本规格中的以下产品决定:

1. Engine 是本机最终历史来源；App Group/SQLite 只保留投影、扩展暂存和迁移档案。
2. 自动写入关闭时仍接收并展示；写入失败只做短暂反馈，不给历史卡片永久报错。
3. 重复内容由再次激活时间移到顶部，快速传输重试不移动。
4. 取消独立置顶和使用次数语义；旧置顶迁为收藏。
5. 明确图片操作显示图片，明确文件操作显示文件；物理类别与展示类型分开。
6. 删除改为可防止迁移复活的软删除，新的用户激活可以复活同一内容。
7. `maxHistoryItems` 迁入 Engine，投影不再独立清理。
