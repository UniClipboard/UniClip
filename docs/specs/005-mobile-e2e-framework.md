# 移动端最小端到端测试框架设计

状态：本机最小框架已实现，双端三轮验收及故意失败验证通过。
日期：2026-09-11

## 目标和完成标准

使用 Maestro 覆盖真实安装的 Expo App。场景表达用户意图，公共操作封装交互，运行环境负责设备与证据。“非脚本式”指不堆砌复制的点击序列，不排斥 Maestro 原生 YAML 声明格式；不增加自己的测试语言或代码生成器。

第一版验收：iOS Simulator 和 Android Emulator 分别运行首次引导及设置往返；每个场景独立准备环境；独立运行和整组运行结果一致；连续三轮通过；故意制造一次断言失败后，退出结果为失败且留下截图、页面结构和运行日志。清理失败或环境准备失败必须使本次运行失败。通过这些检查才可标为框架可用。

## 选择与取舍

采用 Maestro CLI 与原生 Flow、runFlow、条件分支、断言及报告能力。复用 Expo 官方路线，不另建执行器，不将 YAML 转成 TypeScript 或反向生成，也不包装成页面对象框架。

Maestro 已支持公共子流程和参数传递，足以承载第一版的结构化复用。架构体现在职责、依赖方向、状态归属和验收规则，而非采用哪一种文件格式。复杂双设备协调不是第一版需求，不为它引入更重的工具。

先验证现有 SwiftUI / Compose 控件可被 Maestro 定位和操作，再扩展覆盖。设计不代表已验证当前原生 UI 与工具兼容。

## 最小结构

```text
.maestro/
  config.yaml                   仅发现 scenarios 下的可独立场景
  scenarios/
    first-launch.yaml
    settings-navigation.yaml
  actions/
    onboarding/
      complete.yaml             共同入口；仅在确有差异时分派平台
      ios.yaml
      android.yaml
    settings/
      open.yaml
      open-storage-from-trailing-space.yaml
      ios/
        open-storage-from-trailing-space.yaml
      android/
        open-storage-from-trailing-space.yaml
    navigation/
      return-home.yaml
  assertions/
    home-ready.yaml
    onboarding-visible.yaml
    storage-visible.yaml
  lifecycle/
    launch.yaml                 启动并等待应用就绪，不重置设备
    restart.yaml                保留数据，停止后重新启动应用

e2e/
  README.md                     场景目录、前提、运行方式、故障排查
  environment/
    run.mjs                     薄入口：每场景准备→Maestro→取证→释放
    ios.mjs                     测试专用 Simulator 的准备与清理
    android.mjs                 测试专用 AVD 的准备与清理
```

这是职责布局，不要求先创建所有空文件。只有场景用到的公共操作才落地，只有真实平台差异才拆分。保持相同的操作入口；Maestro 使用显式平台条件调用子流程，不依赖 Metro 的文件解析。

依赖方向为 scenarios → actions / assertions / lifecycle；actions 可以调用就绪检查和平台实现。公共操作不得调用场景；平台实现不得反向调用分派入口。公共文件不独立作为场景执行。配置限制发现范围，单场景与整组入口都使用同一个场景目录，实施时验证公共文件不会被误收集。

不新增独立 npm 工作区。YAML 不进入现有 Jest 测试收集；环境入口是普通 Node 模块，只使用所需的系统工具和进程管理，不添加测试业务 DSL。设备准备属于运行基础设施，业务点击只能由 Maestro 执行。

## 三项职责

| 所属位置 | 负责 | 不负责 |
| --- | --- | --- |
| scenarios | 场景前提、公共操作组合、显式调用业务结果检查 | 重复点击序列、平台分支、权限处理 |
| actions / assertions / lifecycle | 有意义的用户操作、稳定定位、可见结果检查、应用启动重启 | 创建设备、改数据库、编排整组测试 |
| environment | 干净设备、安装包、调用 Maestro、结果与证据、清理 | 查找控件、点击页面、实现断言或重试引擎 |

公共操作表达“完成引导”“打开设置”等用户意图，完成时保证目标状态已就绪。场景显式调用结果检查，不把“没有报错”当作成功。检查文件封装可见结果的定位规则，不直接读取数据库判断 UI 已完成。

每个公共操作在文件头说明前置页面、少量输入、完成状态及是否改变持久数据。应用标识由环境统一传入；输入采用 Maestro 原生参数，禁止全局可变业务状态、深层继承或通用点击包装器。单次点击无需机械拆文件；提取必须有复用价值或明确的平台边界。

原生 Flow hooks 仅用于确实共用的应用内准备或收尾，不在嵌套操作中重复清空数据。不依赖 onFlowComplete 处理进程被终止的设备回收；运行入口通过 finally 和终止信号处理尽力回收，自动执行环境仍须有始终执行的清理步骤。

## 第一条完整链路

场景 A：首次引导。

1. 分配本次测试独占的干净模拟设备并安装指定 App。
2. 从真实首次引导进入，按产品已有的无设备连接完成路径操作；实现前核对实际文案和路径，不写入 welcomeCompleted 绕过引导。
3. 验证首页已出现，引导消失。
4. 结束并重新启动同一个 App，保留本场景数据。
5. 验证仍进入首页，不再出现首次引导。

场景 B：设置往返与整行点击。

1. 独立准备干净环境，复用“完成引导”公共操作。
2. 从首页进入设置，点击“存储管理”行右侧空白区域。
3. 验证存储管理页面的独有内容；返回设置，再返回首页。
4. 验证首页可操作。

两个场景不依赖运行顺序，不共享可变业务数据或设备状态。第一版串行运行，每次单独指定一个平台，不先实现多设备并发调度。

## 稳定性规则

- 页面控件使用稳定的测试标识；在原生可访问性树上实际验证其映射，不假设 React Native testID 可以直接用于所有 SwiftUI / Compose 控件。
- 标识由已有共享 UI 控件向对应平台控件传递，不为测试复制 UI。不得为了定位而破坏读屏名称或将整行合并到无法操作。
- 普通交互不使用绝对坐标。整行空白区测试是明确例外：读取该行当前边界，选择行内相对位置，确认该位置属于空白区域，再点击并验证导航。此细节仅由平台公共操作持有。优先核实锁定版本的元素内相对点击能力；不能假定 Maestro 能直接计算任意控件边界。若只能使用屏幕相对坐标，必须固定设备与布局、先确认整行可见并留截图证明落点是空白，再验证导航，不能退化成点击文字冒充整行验证。
- 等待可观察条件，有明确超时；不通过固定睡眠猜测动画或启动结束。不把重试整个失败场景设为默认行为。
- 固定设备型号、系统版本、语言、App 构建版本和测试依赖版本。版本具体值由第一次兼容性实跑确定并锁定，不使用浮动 latest。
- 初版不使用预览界面或伪造 Engine 替代真实应用链路。无需连接的测试保持不加入真实空间。

## 数据和设备隔离

第一版仅运行在可销毁、测试独占的模拟设备上。iOS 使用独立创建或从受控干净模板克隆的 Simulator；Android 使用专用 AVD 的干净数据启动。准备模块必须核对设备所有权，禁止清除开发者正在使用的设备。

仅卸载 App 不足以证明干净：iOS 还有共享容器、钥匙串与扩展状态。用干净设备作为场景起点，不修改应用缓存目录结构。重启保留数据的操作只在单个场景内部执行。

第一版不增加数据库写入入口、任意命令入口或测试专用网络服务。以后需要大量测试数据时另行设计受控准备能力，不能绕过本来要验证的用户操作。

## 构建与自动执行

复用现有 Engine 准备和原生构建流程，测试消费明确路径和版本的安装包。iOS 需要 Simulator 构建，Android 需要 APK。应使用包含应用代码、可独立启动的构建，避免依赖开发服务器是否运行；不以 Expo Go 代替包含自定义原生模块的完整 App。

测试入口接受平台、安装包和场景选择，每个场景准备独立环境后调用一次 Maestro。第一版串行整组执行时，仍逐场景准备干净设备，不能把整目录交给同一台未重置的设备后声称已隔离。直接调用 Maestro 仅供调试，正式验收走统一入口。入口只负责基础设施生命周期和汇总原始退出结果，不解释 YAML、不实现断言或自动重试。已有打包脚本可以保留，禁止在 shell 或 Node 中编排业务点击流程。

先完成本机双平台验收，再接现有 GitHub Actions；iOS 任务使用 macOS，Android 使用具备模拟器加速的环境。构建失败、设备准备失败和业务断言失败分别报告。自动执行调用与本地相同的测试入口，不维护另一套用例。

失败时先收集截图、页面结构、Maestro 日志、可取得的 App 日志，再清理设备；证据采集失败不能覆盖原始错误。报告记录场景、平台、系统、App 版本、测试版本和失败阶段。输出按运行与场景分目录且不提交版本库。正常与失败退出都释放测试设备，清理异常单独报告。

## 本版边界与后续扩展

首版不覆盖双设备互传、真实手机、分享扩展、后台保活或逐帧视觉判断，不为这些尚未实施的能力预建抽象。

每次执行显式绑定测试设备标识，不依赖工具自动挑选开发者当前设备。后续双设备互传需另行设计两端协调和证据关联，届时核对接收端实际内容，而非只检查发送端提示。第一版不预建双设备协调层，也不宣称单设备公共流程天然支持双设备测试。

普通导航断言不能证明动画期间没有短暂闪出父页面。涉及 iOS 嵌套弹窗时仍须独立增加录像逐帧检查，并遵守现有稳定父页面持有弹窗的项目要求。

## 实现顺序

1. 只打通一台 iOS 模拟器上的启动和一个真实控件定位，确认工具与当前原生 UI 兼容。
2. 完成场景 A 的准备、操作、断言、失败证据和清理闭环。
3. 增加 Android 实现，以同一个场景验证职责分离有效。
4. 增加场景 B，验证操作复用与整行空白点击。
5. 执行前述独立运行、连续运行及故意失败检查，再接入自动执行。
