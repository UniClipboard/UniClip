# ADR-001: 打开“我的空间”时先展示已知设备

状态: 已决定，待实施

日期: 2026-08-10

## 背景

“我的空间”用于查看当前空间内的设备及其在线状态。当前应用启动时会恢复空间和
设备信息；打开“我的空间”时也会再次刷新设备列表。

这保证了列表和在线状态尽量新，但在应用刚启动后立即打开面板时，界面尚未拿到
设备列表，只能展示“加载中”。用户不能先查看自己已经知道的设备，且每次打开
面板都会触发一次刷新，造成明显的等待感。

设备名单是空间的长期状态；在线状态和成员变动则可能在短时间内变化。两者不应
采用同一种呈现方式。

## 决定

“我的空间”采用“先展示，后更新”的规则。

1. 应用启动时仍恢复一次空间和设备名单。这是确认当前空间、恢复本机已有信息的
   必要步骤，不能删除。
2. 已经有设备名单时，打开“我的空间”必须立刻显示这份名单，不得用加载状态遮住
   内容。
3. 打开面板可以在后台更新设备名单和在线状态，但后台更新不得阻塞查看、选择或
   管理已显示的设备。
4. 没有任何已知名单时，才显示加载状态。加载失败时，应保留最后一次成功显示的
   名单，并提供明确的重试入口；不能把它替换成空白或“没有设备”。
5. 同一轮应用运行中，已有名单后不因每次打开面板而强制刷新。设备变动、连接状态
   变化、应用回到前台，以及用户主动刷新，才是后台更新的触发时机。
6. 后台更新发现新设备、设备被移除或在线状态变化后，更新当前已显示的列表；不重置
   面板、不清空选择、不弹出阻断提示。

## 结果

### 正面结果

- 用户打开“我的空间”可以立即看到上次已知的设备。
- 冷启动仍会完成必要的恢复，不会把未知状态误当成空空间。
- 网络慢、其他设备离线或更新失败时，用户仍能查看已有设备。
- 应用只在有意义的时机更新，减少无效等待和重复工作。

### 代价与边界

- 刚显示的在线状态可能是上一刻的状态，随后会自行更新。
- 第一次安装、加入新空间后尚未成功获得任何设备名单时，仍需要显示加载。
- 本决定不改变设备加入、移除、邀请或发送内容的规则；也不建立另一份设备名单。

## 不采用的方案

### 每次打开都等待最新结果

拒绝。设备列表的可查看性不应取决于网络和连接恢复，且该做法已经造成用户可感知
的等待。

### 不再启动时恢复设备名单

拒绝。这样会使应用无法可靠确认当前空间，并把所有首次查看都推迟到打开面板之后。

### 定时反复刷新

拒绝。定时刷新不能保证更准确，反而会引入持续的耗电、网络活动和界面变化。应由
明确的状态变化、回到前台和用户操作触发。

## 实施约束

- 设备名单继续由现有空间服务提供；页面只消费它，不自行保存第二份名单。
- 加载状态只表示“尚无可展示的名单”，不表示“后台正在更新”。
- 后台更新必须合并重复请求，避免同一时刻因面板打开和状态变化启动多次相同更新。
- iOS 与 Android 保持相同的行为规则，但各自沿用现有的原生界面实现。

## 验收标准

1. 应用已经恢复过设备名单后，连续打开和关闭“我的空间”，每次都立即显示名单，
   不出现“加载中”。
2. 启动后立即打开“我的空间”时，若尚无可展示名单，显示加载；名单到达后原地更新。
3. 在后台更新期间，已有设备行始终可见且可操作。
4. 更新失败后，已有设备行仍保留，并可由用户手动重试。
5. 设备加入、移除或在线状态变化后，列表会在后台更新；重复触发不会造成重复更新
   或界面闪烁。
6. iOS 与 Android 均覆盖上述场景。

## 实施状态

本 ADR 仅记录决定，尚未改变应用行为。后续实施必须先补齐对应的自动检查，并在
iOS、Android 的实际设备上确认首次打开、重复打开、离线和更新失败的表现。
